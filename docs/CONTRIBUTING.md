# Contributing company knowledge or code

Supply deidentified files only in a public repository. For each proposed example, include what was approved, by whom, what made it strong and which facts were unique. Keep disputed conclusions visible. For a quote, include its actual work basis, date and exclusions. For a locality, identify the jurisdiction rather than a metro-area nickname.

Create a separate extension-pack version for each reviewed change. Add a meaningful held-out case when a new rule could alter calculations, selection, traceability or document language. Record expected behavior before running the model. Do not add a fixed charge merely because it has been allowed on another job.

Code changes should preserve the same model/engine boundary: agents interpret evidence; the engine validates explicit inputs and performs reproducible arithmetic. Review source-integrity, units, quantities, rounding and negative corrections together. Keep optional OCR/rendering dependencies out of the stdlib calculation path.

Before merging: run the tests; run the affected example; inspect the output; update the contract and readiness record. Never describe an unexecuted environment, CI matrix, or professional review as validated.
